# Content Memory Kitchen (CMK) — Memory v0 → SPEC v1

**What this is.** CMK is the Business Memory for The Push / Itay Foyerstein. It's a Postgres "codebase" that content agents read before they write anything. Agents write into it, and the Guardian gates what they write. The source of truth is https://itayfoyerstein.com:
- Promise: *"Your team can do the work. The decisions still come back to you."* The goal is to be *needed at the right level*.
- Audience: EMs, Group Managers, and Directors in growing B2B SaaS. CTOs and VP R&D are secondary, mostly through LinkedIn.
- Offer: 1:1 technical leadership coaching, 12 weeks, 6 sessions, starting with one real situation.

Trust comes first. Nothing is published without Guardian scores and Itay's approval, and the database enforces this.
**Success metrics:** `performance_logs.time_saved_minutes` and `performance_logs.icp_conversations`.
**SPEC target:** idea in → a multi-format package (11 formats) → about 100 pieces/day through a 14-day rotation. See `SPEC.md` and `SPEC_GAP.md`.

## Implementation order

Every phase keeps the v0 trust path: **human at the start, deterministic Spec+Fact gates + editorial review in the middle, human at the end.** The code gates can block missing evidence or broken specs. They don't prove a claim is true, so editorial review and Itay cover that (D1, 2026-11-03). A phase only starts after the one before it has run on real content.

**Phase 0: v0 trust-first (in progress)**
1. **Memory.** Apply `schema.sql`. Itay approves the HE seeds and the 6 site facts. Import 20–50 past posts and mark exemplars. *Status: schema done; facts still draft; past posts not imported.*
2. **Guardian.** Build `guardian(piece) -> GuardianReport` from `guardian_rules.md` and calibrate it on `past_content` **before** any generation. *Status: code gates built; editorial heuristic stub exists but is not calibrated. Run 001 originally used self-estimates.*
3. **Core.** One insight becomes one Core. Guardian checks it, then Itay. *Status: run 001 Core still draft.*
4. **Multiply (2 formats).** LinkedIn `text_post` and `carousel`, HE/EN. *Status: run 001 text B approved; carousel draft.*
5. **Package → schedule → publish (manual) → measure** for LinkedIn, one post/day max.

**Phase 1: SPEC platform (no new formats yet)**
6. Apply migrations 002 and 003. Set `cmk.actor_*` in the runner. Put every agent prompt into `prompt_versions` and have Itay approve them.
7. Measurement loop v1 (`measurement_loop.md`). Itay sets the time-saved baseline. First weekly `measurement_reviews`.
8. Run the Scheduler on the LinkedIn-only plan (`daily_caps {"linkedin":1}`) with per-slot confirmation.
9. Decide the thresholds: score both profiles on 20+ exemplars, then Itay picks (`guardian_thresholds.md`).

**Phase 2: formats, one at a time, text first (lowest risk)**
10. `x_thread`, `poll`, `infographic`. For each one: Itay reviews the stub spec, Guardian checks get added, it's enabled in `format_registry`, it runs for one rotation, then it's measured.
11. `email`. Needs an opted-in list and a sending platform first.

**Phase 3: visual and video (needs MediaProducer + licensing)**
12. `interactive_story`, `broll`, `reel`, `short`.
13. `avatar`. Last, and only after Itay records consent as an approved `boundary.*` fact and the AI-disclosure rules are in Guardian.

**Phase 4: scale toward the SPEC volume**
14. Raise `daily_caps` per channel based on measurement. Batch plan approval. Channel auto-posting adapters, each approved once. The ~100/day target is a ceiling to grow into, and volume never outranks the gates.

## How Codex should use it
- **Read before writing.** Load the active brand_voice, the ICP, the format_spec, the active prompt version, and approved public facts into the prompt context. Never use other sources for factual claims.
- **Write through the contracts.** Validate output against `contracts.md` (v0 + v1) before inserting it. Record every fact used in `content_fact_refs`.
- **Never bypass the gate.** Agents only set `draft`, `in_review` and `needs_changes`. `approved_by` is always a human. If a CHECK or trigger fails, that's the gate doing its job, so don't relax it. Disabled formats and stub specs are gates too.
- **Identify yourself.** Each transaction does `SET LOCAL cmk.actor_type/actor_name/run_id` so `audit_log` attributes the change correctly.
- **Learn from corrections.** Each human edit or Guardian rejection gets a `correction_log` row that includes `rule_candidate`. Three or more repeats lead to a proposed new `version` of brand_voice, format_specs or prompt_versions.
- **Hard rules.** Don't invent pricing, client names, testimonials, numbers or consent. Anonymize case material. Use the voice: evidence before diagnosis, one reversible move, observable change over hype.
- Migrations go in new numbered files under `migrations/`. Never edit an applied file.

## Focused research agents inside CMK

CMK now has separate TopicResearchAgent, HookResearchAgent and ResearchSynthesisAgent roles,
followed by the existing CoreCreator and Repurposer. Each research role has its own approved-prompt
boundary, durable task/output and shared run budget. Deterministic source/claim/spec checks guard the
handoffs; EditorialGuardian remains a heuristic stub requiring human quality review.
See [docs/RESEARCH_RUNTIME.md](docs/RESEARCH_RUNTIME.md) for public-source collection/import,
The Push/management/bottleneck/AI Code Factory focus, source provenance and independent search-fee
permission. Profile and new prompts are seeded draft/inactive. Mock tests do not establish live coverage
or successful hooks; snippets cannot prove original openings or effectiveness.


FactGate limitation: extraction and candidate matching are heuristic. Detected nonliteral factual
wording now blocks for explicit support review; literal matches are not proof of truth. Reports expose
unclassified text and pending human semantic review. Manual handoff rechecks a confirmed slot and a
valid package against the current approved content hash before creating an attempt.
